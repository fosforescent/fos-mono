# web - CLAUDE.md

## Directory Summary
Vanilla-TS task client used in the browser and wrapped by the Tauri desktop/mobile app (`desktop/`). Offline-first: the replica (a FosStore from `shared/sync`) lives in localStorage and merges with the account or another device when connected. Design: `docs/sync.md`.

## Files
- `src/main.ts` - entry; dev-only auto sign-in from `VITE_API_USERNAME/PASSWORD`, never in production bundles
- `src/app.ts` - controller: stored session restore, attachment lookup, sync scheduling (account over HTTP, direct over WebRTC, manual relay), connect/invite/direct flows
- `src/ui.ts` - DOM rendering from app state. **Workflowy-style tree**: there is no add bar; a blank "ghost" row at the top of the view (`renderGhostRow`, not in the replica until typed into) is where the cursor defaults (`focusGhost`), Enter makes it the first row (`App.addRowAtTop`, marker parsed) and opens a row below, ↑ from the first row returns to it. The selected row is an inline editor (click or arrow to it); ↑/↓ move between rows, Enter adds a blank row below, Ctrl+Enter marks a task done (other rows: new row below), Ctrl+Shift+Enter adds a row inside, Tab/⇧Tab indent, Alt+↑/↓ move, Alt+→ zoom in, Alt+← zoom out, Backspace on a blank row deletes it (Ctrl+Shift+⌫ deletes any), Esc leaves, Ctrl+. opens the `⋯` context menu (also right-click), **Ctrl+H toggles the keys/syntax help modal** (`KEY_HELP` + `SYNTAX_HELP`; also the `?` button and the menu). Rows without children show no bullet; only notes keep the `·`. Depth shown at once comes from `maxDepth()`: phones (<640px) show one level and rows with children get a `›` zoom chevron; larger screens expand/collapse 2–6 levels in place depending on height. HTML5 drag-and-drop above/below/into, link panel (members, versions, proposals, presence dots), the **context panel** (`renderContext`: banks in scope, peers with capability chips, assignments per peer), hamburger menu and the `Local` badge beside connection status, Connect/Invite/Requests/Direct/Help modals (QR via `qrcode`, scanning via `html5-qrcode`), and the *Approve a sign-in* modal opened by `?device=CODE` (a `fos login` in a terminal waiting for this browser)
- `src/api.ts` - backend calls (login, node requests `requestPeerNode`, attachment, invites, connect polling, WebSocket events)
- `src/p2p.ts` - WebRTC host/guest with offer/answer codes, sync over the data channel, manual relay codes
- `src/storage.ts` - localStorage adapter: replica, prefs, session (token only)
- `src/rows.ts` - row markers (`parseRowInput`; the list the help shows is `SYNTAX_HELP`): `[ ]`/`[x]` task (`[ ] `name` …` executes a template), `>` note, `//` comment, `-<kind>` requirement where the kind names the child row that fills it (`-[ ]` task, `-$ 50` money / `-: 1h` time / `-# 2 widgets` things / `-@bob` a person, `-?` search, `-market`, `-mail`, `-choice: a | b`, plain `-` confirmation), `$` / `:` / `#` / `@name` allocations with an optional window after the amount (`parseWindow`), `?` query, `@calendar|@money|@inventory|@person name [capacity]` resource bank, `` `name `` template, otherwise a plain row. `rawRowText` rebuilds the marker form for editing; `allocationTag` the tag shown on a parent row; `RESOURCE_MARKER`/`RESOURCE_ICON`; amount parsing/formatting, link/image/YouTube rendering, file download
- `src/timeblocks.ts` - the **time-block picker** (`openTimeBlockPicker`): a zoomable timeline (years › months › days › hours › minutes; ticks zoom in, the scale control and crumbs zoom out) where a block (the amount, hours) is placed inside a window (the span held). Presets ("1h in 8h") pick both and slide to a comfortable level; click/drag on the track places the window (snapped to month/day/hour/15m/5m per level); busy spans of the chosen calendar bank are drawn, nights/weekends hatched. Resolves `{ amount, start?, end?, bank }`. Opened from "Pick time…" on an unmet `-:` requirement (`pickTimeForRequirement` → `applyConstructor` creates the allocation inside) and from the calendar constructor dialog (fills amount/window/bank; the datetime-local fields stay as the fallback)
- `src/style.css` - the whole look: tokens on `:root` (dark is the primary palette from the design canvas, light derives the same roles; `data-theme` overrides `prefers-color-scheme`), IBM Plex Sans/Mono bundled from `@fontsource` in `main.ts`. Header = brand + breadcrumbs + status pill + keyboard help; the tree is a bordered panel; row types are uppercase chips (`kind-badge` needs/ok/query/bank/alloc/tpl); the footer bar carries save state, the Ctrl+H hint and Terms/Privacy. Class names are stable because the tests query them
- `src/notes.ts` - note blocks: frontmatter + child-row variables (`key: value`, titled children, refs to other blocks), `{{key}}`/`{key}` expansion, lists, `.md` export
- `src/markdown.ts` - marked + DOMPurify; KaTeX (`$…$`, `$$…$$`) and Mermaid (```mermaid fences) are dynamic imports loaded on first use
- `src/project.ts` - project mode inside Tauri: finds `fos.config.toml` (`find_project`), keeps state in `<dir>/.fos/` through `read/write_project_file`, follows git branch switches
- `src/filesystem.ts` - desktop-only directory rows (`UnreplicatedRow`, never in the replica): `linkedDirectory` picks the directory a node lists (a "Link with directory" binding in webview localStorage, a `local-repository` argument above, or the project directory at a project window's root, `App.projectRoot`; not `~` in the home context); browsing folders and read-only text previews; **file references** (`referenceFile`, `renderFileReference`): a row of the library type `lib:type:file-reference` whose form fields pin a path relative to the linked directory and the SHA-256 from `hash_node_file` (shared/sync/replica.ts `addFileReference`/`fileReferenceAt`/`setFileReferenceAt`), shown as current / stale (Update reference re-pins) / missing, or "not available on this device" where the directory is not linked. Tests: `tests/filesystem.cjs`, `tests/file-references.cjs`

## Conventions
- Native mobile layout is selected before async startup in `main.ts`, gated by `inTauri()`. Safe-area header/footer padding applies only under `.ios-shell` and `.android-shell`; ordinary browsers have no extra safe-area padding. The phone breakpoint changes the header gutter without overriding native top padding. In the iOS shell, `html`/`body` fill the native containing block and `#app` has `min-height: 100%`; ordinary browser layouts retain `100dvh`. Footer safe-area padding is applied once, inside that minimum height, and longer content can scroll normally.
- The UI never sees content addresses; it reads `viewNode` output (alias ids, titles, flags).
- Rows have a `kind` (`task | plain | note | comment | ref | requirement | supply | query | resource | allocation | template`, see `docs/sync.md`); only tasks are checkable, and a task with unsatisfied requirements has a disabled checkbox and a `needs n` badge. A task made from a template has that template as its row edge's instruction; its view carries `template{id,name}` (badge `` `name ``), and a row whose template has not arrived from its peer yet shows a `reference error` badge and is read-only. Any row can be zoomed into, invited to, or attached to by a device; there is no "partition" concept.
- Editing shows a row's raw marker text (`rawRowText`) and re-parses the whole text on commit: `App.rewriteRowAt` → `setRowContentAt` rewrites kind, text and data in place (id and children kept); allocations resolve their bank through `App.allocationWithBank`/`bankFor` (nearest bank of the type above, the requirement's resource, else the type's default pool = first top-level bank; a person allocation needs a bank only with a window). Each row has a `◉` zoom dot left of the drag handle. Allocations under a row show as tags on it; unmet requirements (and executions/templates with unmet ones) get the `unmet` red mark, allocation requirements a green progress bar (`requirement.have/need`). Dropping an allocation on a requirement supplies it; dropping a template executes it inside; "Add @name as a member" in the menu makes a row a group (`App.addPeerToRow`, fos joins as a member the first time). The blank top row keeps focus after Enter (no extra blank row).
- Rows with controls (requirement, supply, query, resource, allocation) keep their body when selected (`renderSpecialBody`: Confirm / choice buttons, "Apply poll result" on a choice with a poll, "Ask fos to search", "List on the market", "Done (confirm)" for the assigned peer, allocation picker, Search/Refresh, bank balance); double-click or Enter edits their text. Typing a `-`/`?`/`@`/`$`/`` ` `` prefix into a blank row converts it (`App.convertPlainRowAt`); `[ ] `name`` applies the template (`App.applyTemplate`). Allocations resolve their bank from the parent context (`App.bankFor`: bank above, else the bank of the requirement's resource).
- Root and Home: the app starts at Home (`fos:home`, a row of the Home type, which only a device root accepts) beneath root. Rows whose type rejects one of their rows are type errors (shared/sync/patterns.ts): the tree shows them as before, the row and the rejected rows marked red (`.type-error`, `.type-rejected`); a local edit that would make one is refused. Home is told apart by its type (`row.kind === 'home'`), paths by its id. Settings displays root through the same node workspace and row editor, with Home collapsed when entering. Existing Home templates migrate without losing children, peer bindings, or editable branches. Root is not shown in Home’s breadcrumbs. In Settings the crumbs read gear ‹ house: the gear is current and the house leads back to Home. Each device remembers the Home descendant it last viewed as a setting row inside Home (`fos:setting:<peer>:view`, label "Last viewed", shown in Home's tree with a link; `App.savedHomeView`, written by `goTo` without an undo entry) and resumes there on the next visit; local preferences no longer carry the view. Browser history mirrors navigation (`installNavigationHistory` in `ui.ts`, `App.restoreNavigation`), so back/forward move between nodes, Settings and execution views. The execution view offers Complete only for work (requirements, allocations, pending inputs or an evaluation record); tasks have their own Complete/Abort, and content such as notes is only displayed. `tests/navigation.cjs` covers these.
- Node workspace (layout from the design canvas's tree view): a title row with the node name, **Run** (outlined, disabled with a tooltip while `blockedBy` is non-empty), **Add** (focuses the ghost row), the ✎ input toggle (`prefs.input`, shows `.node-input`) and the `⋯` node menu. Contextual actions (Generate subtasks, Confirm/choices, Publish, Connect…, evaluation status) sit below it; capability tabs appear only when there is more than the main set. Placeholders/triggers (`.node-values`) show only when the node has any or is a template. The children toolbar is filter · constructors toggle · labelled Tree/Chat/Grid/Queue switch. The toggle opens the **constructor panel** (`renderConstructorPanel`, `#constructors`, `data-accordion="context"`): peer icon tabs (This device first, then `contextPeers()`, + Add peer, draggable) beside one search over all constructors and nodes; the selected peer's constructors as a draggable icon grid (`constructorGroups`: row-kind seeds like Task/Note/-$/-:/Decision and resources on the device, Ask fos/Search/market on the account, Repository on GitHub, Pull on its peer, handler offers on their peer); typed-value chips for the selected row's unmet input (`suggestedConstructors`, hidden when nothing is needed); then the selected peer's rows (capability chips, sign-in, marketplace search on the account). Row-kind seeds (`seed:<marker>`) fill the ghost row, or a row inside the selected row, or rewrite a dropped-on row.
- Views: tree, direct-child list, card grid, and a chronological comment feed share the existing row editor and graph. Chat input creates comment rows; nested comments include their paths. Child text/capability filters do not mutate data. Search results can link here or be dragged into compatible requirements. Typed placeholders reuse `addRefAt` and existing binding resolution; named custom types are nominal identities (not a new schema editor).
- Node history: the icon controls select the latest change confined to that subtree, refusing changes that also affect siblings (such as cross-parent moves). Changes still merge through the same graph history. Keyboard undo/redo retains the existing session-wide behavior.
- Capability switches store nearer member bindings, so children inherit the node override while parents remain unchanged. Integrations use the same mechanism. The Integration constructor offers GitHub, Google, Stripe and the phone; what each provides (`integrationOffers`) and what the fos server provides (`serverOffers`, `recordServerOffers`) come from the server's handler registry, never from a built-in list, so the palette only shows constructors with a handler behind them. Phone linking is SMS, while QR invitations grant app access; these are distinct existing transports.
- Account form (`renderConnect`, on the fos peer node and in the `connect` modal; `state.authFlow`): Sign in / Create an account tabs on one form; creating asks for username, email **or** phone, password typed twice and the terms; the server answers with where the code went and the form moves to the six-digit code step (`App.registerAccount` → `confirmAccount`, which then signs in with the password typed). Signing in to an unconfirmed account (403 `unconfirmed`) opens the same step. "Forgot password?" emails a reset link (`?reset-password-token=` opens the reset step; `?confirm-email-token=` confirms in one click, both handled in `main.ts`). The settings root groups its rows (Account, Device, Connections, Data) with `li.setting-group` headers; the rows stay ordinary setting rows.
- Fos points: `ff 20` allocates, `-ff 20` requires; `state.points` is the account's token balance (`getTokenBalance`, refreshed after each account sync, shown on the fos row); an `ff` allocation with no `@points` bank draws from it (`resource: 'fos:points'`). `kindPreview` shows a badge after the ghost row's and the editor's input saying what the typed line is recognized as (`describeParsed`).
- Integration peers in node context: `state.integrations` (`listIntegrations`, refreshed after the first account sync and on return) decides each row's button: "Sign in with GitHub/Google/Discord" (`App.connectIntegration` → `startIntegration` → in the browser the page leaves and `main.ts` reads `?integration=&ok=` on return → `App.integrationReturned`; inside Tauri the URL opens in the system browser through `openExternal` (`project.ts`, tauri-plugin-opener) because Google refuses embedded webviews, and `App.checkPendingIntegration` re-reads the integrations when the window regains focus), Disconnect, "Link phone" (the `phone` modal: `App.phoneStart`/`phoneVerify`), Stripe's account status. MCP peers (`state.mcpPeers`, `listMcpPeers`) are rows with "Attach here / to Home" (`App.attachMcpPeer`, also per row in the menu). Requirement buttons ("Ask fos" on `-llm`, "Open issue" on `-repo`, "Run" on `-tool`, "Add to Google Calendar" on a time/person requirement with a window) all go through `App.askPeerAt` → `evaluateAt(requirement path)`: `serverHandles` decides the account server runs it, `evaluateOnServer` sends a `complete` event, and the server's handler registry executes the effect; results arrive with the next sync. An `-llm` result pauses the evaluation as `awaiting-review` until it is accepted in **Context & results** (`decideTaskResult`); "Run with this context" in that modal is the same `complete`.
- Row menu seeds: "Add requirement inside: money/time/things/person/…" and "Add allocation inside" open a row that starts with the marker (`App.addRowInside(at, id, 'plain', seed)`); "Add bank below" seeds `@money `; "Add @name as a member" makes the row a group.
- Allocation bins: "Send to @owner (…) as a proposal" in a row's menu (`App.sendRowTo`) posts the row with its requirement/allocation/task/comment children through `submitMarketProposal` to a node of that account this one knows (`App.knownListings()`: market result refs); the receiver approves it in the link panel.
- Constructor panel peers: the tabs are this device, the Fos server, Triggers, Add peer and the node's own peers; sub-peers (integrations, MCP servers and Fos users under the server; agent CLIs and the local MCP server under the device, `ContextPeer.parent`) are icons in the parent's grid with a status dot (green reachable and granted here, orange granted but unreachable, grey nothing granted; `App.peerStatus`). Clicking a sub-peer opens its own grid with a crumb back; dragging it into a row makes a row with a select of its actions. Opening any peer shows Read / Write / Execute toggles (`App.peerGrants`, `setPeerGrant`; write = edit + approve) in place of the old capability chips; integrations keep their connection line. The MCP servers (`mcp:local`, desktop loopback via `ensureLocalMcp`; `mcp:server`, a scoped hosted credential) expose exactly the tools their grants allow and accept nothing when all are off. There is no separate "Connect to agent" control.
- Local agent peers (desktop): `App.probeLocalAgents` asks `agent_clis` at startup which of `claude`/`codex` are on PATH; each becomes a read-only peer `agent-cli:<provider>` in `contextPeers` (no graph row), nested under the **This device** tab of the constructor panel with its actions as constructors (`action:agent-cli:*` opens the CLI, `action:agent-run:*` runs the SDK when `sdkAvailable`), and the usual child/field masks. Test: `tests/agent-peers.cjs`.
- Shared nodes (`App.openSharedNode`, `sharedNodeAt`, `sharedGrants`, `syncSharedNodes`): a ref row with `refOwner` that another account granted this one capabilities on opens as a live projection provided by the account server as `user:<me>` (`requestPeerNode(session, request, owner)`, `locateSharedNode`); children load through the same provider, local edits sync back as `node-sync` proposals, Run goes to the owner's host (`sendEvent(..., owner)`, needs the `execute` grant, which the header line and the Run button reflect), Analyze reads what is loaded. A listing without a grant falls back to `openMarket`. Test: `tests/shared-node.cjs`.
- Inviting a Fos user: "Add sub-peer" under the fos server in the context panel (`fosUserSearch`, autocompleting `@name` while typing → `App.addPeerHere`) sends an `invite` event through `sendEvent`; the server records the member grant and delivers a request to that user (the inviter as a sub-peer of their fos server, the node as a proposal on the sub-peer's row, a ref row with `refOwner` once accepted). Nothing is written locally; the grant arrives with the next sync.
- Peer policies (`state.policy`, a `PeerPolicy` towards the account server): from `[server] to/from` in fos.config.toml in project mode (`policyLocked`, chips shown locked) or saved in prefs (`App.setServerPolicy`), `DEFAULT_DEVICE_POLICY` otherwise. Enforced in `syncNow` (no round without `from: read`; node sync runs receive-only, `push: false`, without `to: autopush`, so nothing local leaves), `mayPropose()` (`to: edit` gates `sendRowTo`/`submitProposal`) and `readsRequests()` (`from: read-requests` gates the proposals list). Member rows show both directions (`to` = capabilities, `from` = accepts, `App.setPeerCapabilities(id, to, disabled, accepts)`).
- Market: "List on the market" on a `-market` requirement runs the server's `market` effect through `App.askPeerAt` → `evaluateAt` (nothing is flagged or supplied locally); a hit from another account (a query with `market: true`) is a ref row with `refOwner` that opens the **Market listing** modal (`state.market`, `App.openMarket`/`submitProposal`): the owner's rows, the requester's own proposal, a comment box and a picker per allocation requirement over `App.allocations()`.
- Drag and drop: plain drag moves, **Alt+drag places a reference** (row shows the 🔗 icon), **Ctrl/⌘+drag places a deep copy** (⧉). Modifier keys are read at drag start.
- Voice notes: the 🎙 button below the breadcrumbs records with `MediaRecorder`, capturing the path when clicked and posts the blob to `POST /user/data/voice-notes` (needs a session); the result is inserted at the captured path and becomes a parent note (summary) with a note per sentiment cluster, its points as plain rows, and a transcript note.
- Icons: `public/favicon*.png|ico`, `apple-touch-icon.png`, `icon-192/512.png`, `site.webmanifest` are generated from the tree logo (`frontend/logo3-bare.ico`, 256px, the largest copy in the repo).
- Replica operations return a new replica object; always use the returned value.
- `tsconfig.json` deliberately omits `erasableSyntaxOnly`/`noUnused*`/`verbatimModuleSyntax` so the graph code in `shared/` compiles.

## Zoomed nodes and evaluation
The zoomed node has a persistent full-text textarea above its children. Its draft/caret survive sync; saving uses the existing three-way merge. Child filters keep matching subtrees visible, and node search links compatible local values using existing refs/supplies. Template placeholders are neutral until instantiated. Peer-backed actions use live availability as well as the node's inherited offers.

The green Evaluate action uses the shared evaluator. Local tasks run in the client; GitHub issue effects run at the account server after syncing and validating the reviewed node. LLM results still require the existing human review flow; other unimplemented executors block rather than mark requirements fulfilled. Evaluation journals are not ordinary undo entries. Review recovery creates/checks manual compensation tasks before unlocking a failed transaction.

Device timers, parent-completion, and on-request triggers run while that owning app is open. They do not replay failed/uncertain occurrences automatically. Server cron appears only when advertised by an enabled scheduler. Trigger settings and execution records are typed document refs, not additional row kinds.
Device trigger execution requires the browser's Web Locks API (available in supported browsers on secure origins). It holds a lock for the device and checks persisted occurrence state so duplicate tabs do not run the same trigger concurrently. The poller caches configured triggers by graph head and checks only due occurrences.


Trigger palette entries can be clicked or dragged to create a child template with the existing trigger configuration. Invalid schedules do not create partial rows. Existing triggers can still be paused/rearmed from their node. Device triggers require Web Locks and an open owning app; cron requires an advertised server scheduler.

Validation: `npm test --prefix web` covers the workspace, scoped history, inherited offers, integration choices, placeholders, chat/filter behavior, and previous account/sync/focus regressions. Browser layout smoke checks should include 390px and 260px widths with the accordions expanded.

`src/sharing.ts` handles `#share=` URLs and the Peers → Share by URL controls. A successful visit creates/reuses an ordinary host-peer node in Home with a foreign-ref child; opening that child renders the remote input handler below the normal node controls. It preserves the visitor's own session and context. Public polls ask anonymous visitors for a display name; account-only links require sign-in. Local search/drop supplies only the declared text/allocation projection. Anonymous source links stay in the local context; signed-in source links stay in that user's account. `tests/sharing.cjs` checks URL routing, Home/Host placement, anonymous input, return visits and local source projection.

Row branching and child navigation use `src/combobox.ts` through `src/alternatives.ts`: a searchable, grouped popover beside the existing editor. Arrow keys/Enter select; Escape returns to the trigger. Typing a name offers branch creation or adding a child through existing App operations. Proposal previews remain read-only and offer copy-to-edit. Popup search focus survives sync renders.

Settings use `view(..., true)` to project stored typed setting refs and peer bindings as ordinary row identities. `settings.ts` supplies display labels; row handlers reuse permission checks, connection forms, reset confirmation, sessions and YAML operations. Opening Settings migrates missing peer aliases and older connection tool refs to the existing peer capability. Installed defaults are recorded in a hidden document ref so deletion is respected on subsequent visits. Peer controls opened from a constructor use its parent context. Node-values search uses the shared combobox with draggable result options and existing compatibility/link operations.

## Peer and branch editing
- `@name` remains a person allocation; `@{handler}` creates an ordinary row backed by a peer-typed mutable ref. Typing `@{` opens the shared combobox's autocomplete in the existing cell. Handlers reuse invite/direct/virtual/account/integration connections. The connection-type dropdown and duplicate peer-creation menu flows are replaced by peer rows.
- Shift+Enter creates a selected content-addressed branch of the current row. Alt+Enter inserts a newline; Enter then Tab creates a child. The branch caret lists local and incoming branches together, without child creation/navigation or a separate proposal section. Incoming branches remain read-only until copied.
- Pull-request buttons toggle a typed `request merge` approval argument on each local branch constructor. This records intent; it does not merge or grant authority. Received branches use the same approval argument while retaining protocol compatibility.
- Invite errors appear in the dialog with Retry; successful codes are selectable/copyable. Late responses from a previous data session are ignored.

Change template is a single row/node menu action. Its modal reuses the shared combobox and offers common constructor icons; + creates a named/iconed template in the current parent or Home, links the source, and opens the definition. Double-click an amount/choice requirement badge (or Enter/Space when focused) to expose named outputs; drag an output to a row or compatible argument. Amount slices remain planned until fulfilled. `tests/templates.cjs` covers the picker, matching carets, linked template creation, split bounds and property drops.

## Row workspace and clipboard
Connect/Offline navigates to the Fos peer constructor in Settings, whose Node actions host the shared sign-in/registration form. Registration calls the existing account endpoint with explicit terms acceptance and then uses the normal isolated login path. Context menus contain only Change template, Add choice, and Link. Branch pickers appear only for existing branches or incoming proposals, in rows and the zoomed header; no duplicate action-area picker. The template modal's pencil opens the linked definition (built-ins remain code-defined).

Ctrl/Cmd-click toggles row selection; Shift-click selects a visible range. Copy emits indented marker text for the visible selection. Link emits a local `fos-ref:` handle; pasting into a blank row uses `addRef`, and opening a local ref navigates to its shared source. Structured paste (`paste.ts`) handles Markdown headings/lists/tasks/code blocks and YAML maps/lists with bounded depth/count and disabled aliases. Existing node-document YAML uses the validated importer. Pasting into populated cells adds children; blank cells accept replacement/root rows. Missing allocation banks retain unbound values for later resolution.

Tree/grid/chat/queue share the children area; List is removed. Chat collects descendant comments newest-first with location links; Queue collects open descendant tasks shallowest-first. The single filter supports `type:<kind or capability>` plus text and datalist suggestions. Triggers have one draggable selected dropdown; placeholders use the common template/type combobox and drag/drop. Version counts live in Node context, and legacy history setting rows are hidden. `tests/row-workspace.cjs` covers these flows alongside existing regressions.

### Node input workspace
- Input/edit (✎ in the title row) owns the text editor, scoped undo/redo, voice, picture/video organization, file attachments, Import, Export YAML. Pull is inserted from the constructor panel, then evaluated through the existing effect journal; automatic sync remains independent.
- Picture/video input captures its destination and data session before uploading to the existing authenticated media-note endpoint. Results become ordinary child notes. Files instead become downloadable `fos:attachment` named values on normal child rows (base64, 1 MB per attachment while browser storage backs documents).
- Import opens a Markdown/YAML file dialog (1 MB); YAML node-document exports retain their graph importer, ordinary YAML/Markdown use the clipboard tree parser. Uploads never follow navigation into another data session.

### Constructor palette
The Standard library tab reads templates from the current library projection or offline bundle (`App.libraryConstructors`), including their titles and stored icons. The same entries appear in constructor search and task-input suggestions. Additions, renames and deletions follow the library node; the Manual handlers group remains in requirement fallback controls. Click/drop instantiates by template identity, preserves a dropped-on row's title and children, and adds an execution inside requirements. Typed inputs validate the template type, incomplete downloads cannot instantiate, and the whole change uses one undo entry. Device primitives and advertised peer handlers remain in their existing tabs. `tests/library.cjs` covers discovery and composition.

The constructor panel's Add peer button is a draggable handle; This device holds inventory/calendar/money allocations and resource banks; the search includes every built-in. Click adds a child; drop onto an ordinary row applies the constructor while preserving its children; drop onto a requirement preserves it and creates a child value. Typed argument targets validate the constructor capability and use the existing ref proposal/application path.

A single parameter dialog captures the destination/session and gathers handler, resource type, amount/unit, optional time window/source bank, or repository name. Applying it uses existing peer refs, row resource/allocation documents, and repository bindings (`App.applyConstructor`), grouped into one undo. Banks and allocations remain ordinary editable rows. Repository binding adds the existing GitHub peer and exposes repository actions; GitLab is explicitly unavailable until a handler exists. No new external integration or execution engine is introduced.

### Unified constructor discovery and effects
- `constructorOptions` combines resource/peer definitions, available triggers, Pull, and active search/LLM/market handlers. Click creates a row beneath the selected node (or current node); drag into a typed input composes via the existing mutable-ref proposal/application path, with a type check. The picker does not dispatch effects.
- Pull is an existing `tool` requirement with `tool: fos.pull`, targeting the active document transport. The browser evaluation driver performs a receive-only sync, adds the unit result supply, and uses the normal effect/recovery journal. Local Pull and server integration effects must be evaluated separately.
- Trigger constructors reuse `configureTrigger` and the existing workflow template/ref representation. Menu-created triggers start paused; schedule errors and incompatible input types leave the graph unchanged. Legacy direct trigger configuration retains its existing enable behavior.
- Editor operations (undo, text/media input) remain controls in the same menu; they do not become workflow effects. Execution and recovery controls inspect/evaluate constructed rows.

## Standard library (2026-10-17)

Notes use the `.fos` definition `lib:type:note` (text body field plus open child rows). Render Markdown and choose multiline editing from `TaskView.text`, projected from the pinned definition's `form.text`, rather than testing the row's native kind. New notes project as plain graph rows; compatibility input syntax still accepts `>`. Execute view substitutes scoped bindings and omits product fields already represented by their parent's projection. Tests cover an unfamiliar Markdown constructor, legacy migration, nested notes, and same-named fields/bindings. The full recursive note-function model remains pending.

The device root ships the standard library as its `fos:library` row, filled from the build (`ensureDeviceLibrary` in `App.withRootContext`); on the desktop every window's store is a device root (Home's and each project's), linked with the other `.fos` stores on the machine at start, both sides (`linkLocalStores` in `project.ts`, the `link_local_stores` command, `App.linkLocalStores`); a linked store appears under its entry in Settings as a peer-held row, and nodes opened from it are read and edited through node exchange on its file (`App.localStoreProvider`, `App.syncLocalStores`, `meta.heldNodes`); a browser virtual-peer document is nested in the browser's device root instead (`config.deviceRoot`, `nestScope`). People who contribute add the shared library to Home ("Contribute to the standard library" on the shipped row, `App.contributeToLibrary`, address from an optional server bundle); that `fos:library` reference in Home renders as "📚 Standard library" (opens the live projection) with an "Updates" link (the shared vote view on proposals). `syncSharedNodes` opens it on the first online sync and `materializeSharedTree` pulls the whole tree, so its templates are in the local replica and instantiate offline (`findTemplateByName` searches the whole replica). `tests/library.cjs` covers the flow against a fake server. The build compiles the checked-in `.fos/library.json` graph with `scripts/compile-library.cjs`; there is no network pull or code-defined seed fallback. Author the local tree with the Fos CLI and use `fos . library export --local --out .fos/library.json` to update the build source. The library's "Manual handlers" rows (`manualHandlersFor`) become buttons on any unsatisfied requirement of their kind (`manualControls` in ui.ts, tree and execution views): `App.applyManualHandler` records a receipt allocation plus supply for allocations (a place from the typed name or, for `lib:device:location`, from `navigator.geolocation`) and a supply by the person for every other kind. `at <place>` / `-at <place>` are the location allocation and requirement (`rows.ts`, resource `location`).
