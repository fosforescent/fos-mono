# shared/sync - CLAUDE.md

## Directory Summary
Offline/online sync on top of the hash-consed FosStore: identity-keyed
three-way merge that turns divergences into CHOICE nodes, node exchange
(node-provider / node-sync), and the device replica. Shared by the web client (and through it the
Tauri desktop/mobile shell) and the backend. Design: `docs/sync.md`.

## Constraints
- Must compile under the `shared/`, `web/` and `backend/` tsconfigs (no enums, no parameter properties, extensionless imports).
- Replica operations mutate the store and return a new replica object; never keep using an older replica object after an edit.
- A row's type is its edge's left node; there is no row kind. Native behaviour (done state, references, flows, queries, banks, templates, patterns, Home, store roots) is chosen by type identity. The old row-kind primitives (COMPLETION, DESCRIPTION, DOCUMENT, COMMENT, LINK, REQUIREMENT, SUPPLY, QUERY, RESOURCE, ALLOCATION, TEMPLATE, LIST) stay in `dag-implementation/primitive-node.ts` because primitive content is part of every cid (never edit their descriptions) and the v2→v3 migration recognises them; a few are still used as types (DOCUMENT for text arguments, TEMPLATE for published template handlers, LINK inside evaluation values). Sync bookkeeping uses `choiceTarget`, `optionNotSelectedConstructor`, `conflictBaseNode`, pointer constructors, `previousVersion`, `mergeSourceNode`, `peerField`.

## Invariants
- The only cids node exchange carries are pinned templates (`NodeChild.template`), pinned grants of member entries (`NodeChild.pinned`) and their content (`templates`/`templateNodes`): a shape pinned to another cid format is refused (`validateNodeShape`, "update the app") and `importNodes` only accepts current-format nodes that verify.
- Equal content ⇒ equal cid on every peer (CID v4 canonicalizes data keys but preserves row order and direction).
- A thing is either a task (or legacy plain node) edge or inside a CHOICE edge under the same alias id, never both.
- After a node's sync, `meta.nodeSync` holds the shape both sides agreed on for it; `isDirty` compares against it. Node exchange never sends history, proposal contents, reference targets or descendants.

## Node evaluation and triggers
- `bindings.ts` accepts a runtime `isPeerActive` predicate. Recursive binding resolution checks explicit and inherited handlers; connectivity is not stored as a permanent grant. `capabilityPeers` distinguishes handler offers from permissions granted to peers.
- `evaluation.ts` checks bindings, conflicts, instructions, and overlapping resource allocations; opens parents first and commits children first. It stores its journal as a named document ref (`fos:evaluation`). Completion is staged until all commits succeed. Handler effects are journalled before dispatch; failed/uncertain effects without compensation produce ordinary recovery tasks. Interrupted evaluation cannot automatically repeat. Executor drivers must serialize evaluation and recovery, persist before dispatch, and revoke their own graph results when compensating.
- `triggers.ts` uses the same typed refs for configuration and occurrence state. Timers belong to one device; parent-completion and incoming-proposal triggers use that device's observed events. A template trigger instantiates the existing template and evaluates the instance. Failed/interrupted occurrences require review. Runtime journals are not cloned; instantiated templates do not inherit scheduling declarations.
- Cron supports five numeric UTC fields, lists/ranges/steps, and the day-of-month/day-of-week OR rule. The current scheduler checks the current minute (no missed-run replay) and the server's default branch selections.


Home normalization keeps `fos:home` as an ordinary plain container, not a workflow template. Legacy Home template edges are converted without changing the node identity or children. Editable Home choice wrappers must be preserved across normalization and reload; context tests cover branch isolation as well as idempotent legacy migration.

`view(..., true)` / `viewNode(..., true)` opt into constructor rows for Settings: named setting refs and existing member/device edges are projected with their stored aliases; default evaluation/content views remain unchanged. Peer constructors carry stable aliases. Settings deletion uses ordinary ref-child deletion, while member/device deletion removes the existing bookkeeping edge on the parent identity.

Branch choice pointers may carry a named `request merge` typed approval ref. `ChoiceOption.requestMerge` projects that child; branch edits, copying and serialization preserve it. Three-way merges retain a request toggled concurrently with branch content. Received branch constructors reuse the same approval child; existing proposal wire/authorization APIs remain compatible. Peer constructor syntax `@{handler}` is excluded from single-brace text parameter parsing and substitution.

Requirement destructuring (`destructure.ts`) uses named typed refs whose existing `ref` field identifies the source requirement. Amount outputs are bounded planned slices, unavailable until source fulfillment; choice outputs expose exactly one selected option. Bind outputs to ordinary record arguments or an allocation's `amount` argument. Resolution follows the current source and refuses removed outputs. Fulfilled amount requirements participate in allocation capacity checks as derived banks. Template instantiation remaps owned source identities and supports ordinary record rows; it copies the definition at application time, not live inheritance.

## Graph-defined comments and notes (2026-10-19)

- `.fos/library.json` is the portable library graph exported from the CLI tree. `scripts/compile-library.cjs` validates its CIDs and compiles `shared/sync/library.generated.json` before web/shared/backend builds and desktop core builds. No network or TypeScript definition fallback. `legacy-row-types.ts` reads old discriminators only; the graph source rejects `instanceKind`.
- `forms.ts` expands parameter rows into ordinary mutable refs, validates scalar inputs, and projects title/attribution from named fields. `addConstructedRow` accepts any graph definition; its rows carry that type. List entries carry explicit positions. Native leaves currently cover text, peer, number and time.
- Comment creation and edits use these definitions. Scalar editors preserve literal row markers. Fields travel through ordinary node-by-node sync, and copying preserves fresh mutable refs. Library exports include both instruction and target dependencies.

Rows constructed from a definition are rows of that type. `ui.ts` recursively builds controls from the pinned definition parameter rows (labels, native scalar controls, products and repeat controls).

No library definition carries `behavior` or `instanceKind` (the compiler rejects both). The client projects `TaskView.text` from the pinned definition and supplies generic text/Markdown rendering. `>` and `addRow(…, NOTE_TYPE, …)` resolve the graph definition; notes pinned to the retired alias-less seed type are rebuilt as values of the graph definition by cid migration v5. ## Row types, no row kinds (2026-10-20)

A row is the edge `[type, row]` and its type is the left node: a standard-library row type (`lib:type:…`; every pinned version shares the type's graph identity, `data.alias.id`) or a template row's content (the type of the tasks made from it). Nothing else says what a row is: there is no `RowKind`, `TaskView.kind`, `instanceKind` or `behavior: builtin:*`.

- Reading (`graph.ts`): `rowTypeOf(store, edge)` (the left node, through branches and type errors; a peer-held stub reads as a reference; null for non-rows: a sync primitive's edge, a choice, a typed argument slot), `typeIdOf(store, typeCid)`, `rowTypeIdOf`, `isRowEdge`, `isRowOfType(store, edge, typeId)`, `rowsOfType`, `isLibraryType(store, typeCid, typeId)`, `isTemplateType`, `isTaskRow` (Task type or a template's instance: done state, blockers, checkbox), `isAllocationRow`, `childRows` (cid, edge, type id, value).
- Resolving and creating: `rowTypeAt(store, typeId, at)` (nearest library; a library seeded before the type existed falls back to the build's definition; throws with no library above), `libraryTypeAt` (same, also outside any library), `resolveRowType` (a cid is used as is). `addRow(r, at, type, …)`, `rowEdgeAt`, `setRowContentAt`, `setRowType(…, extras)`, `rowContent(typeId, …)`, `convertRowContent(value, typeId, now, extras)` take a type id or cid; `keptRowType` keeps a row's own type (a template instance stays a task, a form type stays when re-parsed as plain).
- Views: `TaskView.type` (graph identity, '' for a type without one), `typeCid`, `typeName` (the type's description, for labels), `checkable`. A row of a type without identity reads as a row of no known type: no checkbox, no Markdown, no type errors (`acceptsChild` accepts anything under it). Stored rows of the retired types (the alias-less v3/v4 seed, library types with `builtin:` behaviors, seed notes and comments, money as plain allocations) are re-pinned by cid migration v5 (`dag-implementation/migration-v5.ts`); outside the frozen migrations no code reads those markers.
- Flows: `lib:type:allocation` and `lib:type:allocation:money` (`ALLOCATION_TYPES`). `flowOf(typeId, value)` reads an allocation row by sign: negative = requirement, positive = supply (a handler's answer) or a plain allocation. A money row is told apart by sign alone: negative = a request for payment, positive = a payment (supply and allocation at once). The payment handler (`backend/sync/hostHandlers.ts`) takes money rows with a negative amount; settlement (`payments.ts`) and visitor/manual money inputs write a positive money row under the request, which fills it, and no separate supply. Points and other resources stay allocations.
- Node exchange: `NodeChild = { id, address, template, held? }`; the template is the type. `held` (a reference row or a node a third peer holds) replaces the old `kind: 'ref'`; unloaded stubs record it as `ref.held`. Reference-error stand-ins record only the missing cid.
- Published revisions hash `{ id, title, type, depth }`, so votes cast against revisions from before this change no longer count.

## Member edges travel by node exchange (2026-10-20)

Member entries (`[MEMBER, entry]`, `fos:peer:<peer>`) are children of their node in node exchange and sync in their own rounds, under the grants and masks that already apply: the owner's devices receive and push all of them (market listings, published offers, invitations, switches), another peer receives only its own entry and the rows it may read (a masked projection: a different-looking node with a subset of children). In an entry, grants and offers are `NodeChild.pinned` (the cid of their immutable node, content with the shape). Nothing else changed on the wire. Consequences: relay queues are ordinary rows of the recipient's entry (no step-in path, no `relayQueueSync`); the server's verify key is a row on the fos member entry of the account root again (no Home key row), which an owner's device pulls above Home (`NodeSyncContext.above`). Members granted `local` stay on the machine. Design: docs/sync.md, "On-demand node providers" and "Node sync".
