# shared/sync - CLAUDE.md

## Directory Summary
Offline/online sync on top of the hash-consed FosStore: identity-keyed
three-way merge that turns divergences into CHOICE nodes, node exchange
(node-provider / node-sync), and the device replica. Shared by the web client (and through it the
Tauri desktop/mobile shell) and the backend. Design: `docs/sync.md`.

## Constraints
- Must compile under the `shared/`, `web/` and `backend/` tsconfigs (no enums, no parameter properties, extensionless imports).
- Replica operations mutate the store and return a new replica object; never keep using an older replica object after an edit.
- A row's type is its edge's left node; there is no row kind. Native behaviour (done state, references, flows, queries, banks, templates, patterns, Home, store roots) is chosen by type identity. The old row-kind primitives (COMPLETION, DESCRIPTION, DOCUMENT, COMMENT, LINK, REQUIREMENT, SUPPLY, QUERY, RESOURCE, ALLOCATION, TEMPLATE, LIST) stay in `dag-implementation/primitive-node.ts` because primitive content is part of every cid (editing their descriptions changes every cid, which needs a new data version, docs/cid-versioning.md); a few are still used as types (DOCUMENT for text arguments, TEMPLATE for published template handlers, LINK inside evaluation values). Sync bookkeeping uses `choiceTarget`, `optionNotSelectedConstructor`, `conflictBaseNode`, pointer constructors, `previousVersion`, `mergeSourceNode`, `peerField`.

## Invariants
- The only cids node exchange carries are pinned templates (`NodeChild.template`), pinned grants of member entries (`NodeChild.pinned`) and their content (`templates`/`templateNodes`): a shape pinned to another data version is refused (`validateNodeShape`, "update the app") and `importNodes` only accepts nodes of the current data version that verify.
- Equal content ⇒ equal cid on every peer (cids canonicalize data keys but preserve row order and direction).
- A thing is either a task (or legacy plain node) edge or inside a CHOICE edge under the same alias id, never both.
- After a node's sync, `meta.nodeSync` holds the shape both sides agreed on for it; `isDirty` compares against it. Node exchange never sends history, proposal contents, reference targets or descendants.

## Node evaluation and triggers
- `bindings.ts` accepts a runtime `isPeerActive` predicate. Recursive binding resolution checks explicit and inherited handlers; connectivity is not stored as a permanent grant. `capabilityPeers` distinguishes handler offers from permissions granted to peers.
- `evaluation.ts` checks bindings, conflicts, instructions, and overlapping resource allocations; opens parents first and commits children first. It stores its journal as a named document ref (`fos:evaluation`). Completion is staged until all commits succeed. Handler effects are journalled before dispatch; failed/uncertain effects without compensation produce ordinary recovery tasks. Interrupted evaluation cannot automatically repeat. Executor drivers must serialize evaluation and recovery, persist before dispatch, and revoke their own graph results when compensating.
- `node-values.ts` projects native objects/lists to ordinary rows: `[left, right]`, with scalar leaves. The left can be a type, data constructor, capability or function; the right can be its argument, handler or composed function. An argument is the right node, not a separate slot category. `writeNodeValue` preserves field identity; `readNodeValue` reads graph structure (legacy JSON descriptions are read-only compatibility). Fields participate in row editing, property lookup, forms, merge and masked node exchange. Type definitions travel with declarations; descendant values load separately.
- `triggers.ts` discovers observer primitive declarations by scope, through the same ref discovery as other handlers. A configured trigger pins the selected declaration as its left/instruction node and stores configuration as graph fields on the right. The runner invokes that primitive's observer; it does not dispatch on trigger names. `trigger-primitives.ts` supplies native clocks and event observations. Their patterns carry `triggerDefinition` presentation/scheduling metadata; the menu derives provider sub-tabs from these declarations. Removing or disabling a declaration stops its triggers, and restoring native meanings after reload never republishes it. Failed/interrupted occurrences require review. Runtime journals are not cloned; instantiated templates do not inherit scheduling declarations.
- Cron supports five numeric UTC fields, lists/ranges/steps, and the day-of-month/day-of-week OR rule. The current scheduler checks the current minute (no missed-run replay) and the server's default branch selections.


Home normalization keeps `fos:home` as an ordinary plain container, not a workflow template. Legacy Home template edges are converted without changing the node identity or children. Editable Home choice wrappers must be preserved across normalization and reload; context tests cover branch isolation as well as idempotent legacy migration.

`view(..., true)` / `viewNode(..., true)` opt into constructor rows for Settings: named setting refs and existing member/device edges are projected with their stored aliases; default evaluation/content views remain unchanged. Peer constructors carry stable aliases. Settings deletion uses ordinary ref-child deletion, while member/device deletion removes the existing bookkeeping edge on the parent identity.

Branch choice pointers may carry a named `request merge` typed approval ref. `ChoiceOption.requestMerge` projects that child; branch edits, copying and serialization preserve it. Three-way merges retain a request toggled concurrently with branch content. Received branch constructors reuse the same approval child; existing proposal wire/authorization APIs remain compatible. Peer constructor syntax `@{handler}` is excluded from single-brace text parameter parsing and substitution.

Requirement destructuring (`destructure.ts`) uses named typed refs whose existing `ref` field identifies the source requirement. Amount outputs are bounded planned slices, unavailable until source fulfillment; choice outputs expose exactly one selected option. Bind outputs to ordinary record arguments or an allocation's `amount` argument. Resolution follows the current source and refuses removed outputs. Fulfilled amount requirements participate in allocation capacity checks as derived banks. Template instantiation remaps owned source identities and supports ordinary record rows; it copies the definition at application time, not live inheritance.

## Standard library and audience membership

- `library.ts`: the library is a mutable ref found by what it holds (`isLibraryRef`/`libraryRowOf` in graph.ts: a ref whose value defines the Library type); `ensureDeviceLibrary` gives a device root its Library-typed row from the build, a later build's library being the fos peer's submission (`submitLibrary`); `libraryPath` is the nearest one; `exportLibrary`/`exportLocalLibrary`; `manualHandlers` (a fallback whose row names a native implementation, a primitive, runs on the device).
- `graph.ts` `memberFor`: audience members are implicit groups (`audience:users` = every `user:*`, `audience:public` = everyone); `hasCapability` and every grant walk use it. `sharing.ts` `participants` reads each member's participation record (the sharing handler's result on its member entry); visitors' approvals are approval rows (`acceptSubmission`), counted from the submissions.

- CLI authoring: `fos . ls <library row id>`, `fos . ls lib.comment`, `fos . node lib.comment --out definition.json`; edit data/children, then `fos . node lib.comment --write definition.json`. Add definitions with `fos . node lib.example --under lib --template lib.template --write definition.json`. Files may include CID-validated `nodes` dependencies. Export with `fos . library export --out .fos/library.json`, then `node scripts/compile-library.cjs`. Local device/session/replica files remain ignored.

## Triggers without a schedule (2026-10-20)

A timer or cron trigger is made with no schedule (`missingSchedule`): it never fires (`triggerOccurrence`), cannot be enabled (`setNodeTrigger`), and its row reads as unmet until the schedule is set on its node.

## Rows a peer adds to a shared node (2026-10-20)

A peer editing another account's node pushes its new rows into its submission there, where the account keeps them as references held by that peer (`user:<me>`). The client reads children listed as held by itself as its own rows (`node-sync.ts` `ownHeldChildren`, applied in `App.syncSharedNodes`), the provider serves a node held by the requester blank on a plain pull (`node-provider.ts`), and a never-synced row whose remote is blank (`isBlank`) takes that as its baseline, so its content is pushed and fills the reference. The owner then previews and merges the rows with their content. Test: `web/tests/flows.cjs`.

## File references (2026-10-20)

- `lib.fileReference` (in `.fos/library.json`, fields `path`/`sha256`/`size`) is the row type of rows that reference a file in a directory linked on some device. `replica.ts` `addFileReference` instantiates it with `addConstructedRow`; `fileReferenceAt` recognises a reference only by its edge's left node (`graph.ts` `isLibraryType`, any version of the type); `setFileReferenceAt` rewrites the field values in place. `graph.ts` `libraryTypeAt` resolves a library type by id like `rowTemplate` (nearest library), falling back to the build's definition for libraries seeded before the type existed. ## Row types, no row kinds (2026-10-20)

A row is the edge `[type, row]` and its type is the left node: a standard-library row type (`lib.<type>`; every pinned version shares the type's graph identity, `data.alias.id`) or a template row's content (the type of the tasks made from it). Nothing else says what a row is: there is no `RowKind`, `TaskView.kind`, `instanceKind` or `behavior: builtin:*`.

- Reading (`graph.ts`): `rowTypeOf(store, edge)` (the left node, through branches and type errors; a peer-held stub reads as a reference; null for non-rows: pointer/history/policy edges or unresolved choices; typed right refs and native constructors remain rows), `typeIdOf(store, typeCid)`, `rowTypeIdOf`, `isRowEdge`, `isRowOfType(store, edge, typeId)`, `rowsOfType`, `isLibraryType(store, typeCid, typeId)`, `isTemplateType`, `isTaskRow` (Task type or a template's instance: done state, blockers, checkbox), `isAllocationRow`, `childRows` (cid, edge, type id, value).
- Resolving and creating: `rowTypeAt(store, typeId, at)` (nearest library; a library seeded before the type existed falls back to the build's definition; throws with no library above), `libraryTypeAt` (same, also outside any library), `resolveRowType` (a cid is used as is). `addRow(r, at, type, …)`, `rowEdgeAt`, `setRowContentAt`, `setRowType(…, extras)`, `rowContent(typeId, …)`, `convertRowContent(value, typeId, now, extras)` take a type id or cid; `keptRowType` keeps a row's own type (a template instance stays a task, a form type stays when re-parsed as plain).
- Views: `TaskView.type` (graph identity, '' for a type without one), `typeCid`, `typeName` (the type's description, for labels), `checkable`. A row of a type without identity reads as a row of no known type: no checkbox, no Markdown, no type errors (`acceptsChild` accepts anything under it). There are no stored rows of retired types to re-pin: data from before data version 0.0.1 is not readable (docs/cid-versioning.md), and no code reads the retired markers (`instanceKind`, `behavior: builtin:*`) as row discriminators.
- Flows: `lib.allocation` and `lib.money` (`ALLOCATION_TYPES`). `flowOf(typeId, value)` reads an allocation row by sign: negative = requirement, positive = supply (a handler's answer) or a plain allocation. A money row is told apart by sign alone: negative = a request for payment, positive = a payment (supply and allocation at once). The payment handler (`backend/sync/hostHandlers.ts`) takes money rows with a negative amount; settlement (`payments.ts`) and visitor/manual money inputs write a positive money row under the request, which fills it, and no separate supply. Points and other resources stay allocations.
- Node exchange: `NodeChild = { id, address, template, held? }`; the template is the type. `held` (a reference row or a node a third peer holds) replaces the old `kind: 'ref'`; unloaded stubs record it as `ref.held`. Reference-error stand-ins record only the missing cid.
- Published revisions hash `{ id, title, type, depth }`, so votes cast against revisions from before this change no longer count.

## Member edges travel by node exchange (2026-10-20)

Since 2026-10-22 a membership is a row of the node's content whose left is the peer's node (`peerNode(store, peerId)`: `{ peerId }`, content addressed, an opaque label) and whose right is what the node keeps for that peer (grants for now, its rows). There is no MEMBER primitive and no id derived from the peer: a membership's id is its row's alias, and a peer listing a membership for a peer this side already has is reused (`installMembers`; a membership syncs with the provider's own membership of the same peer whatever its id there: `NodeSyncContext.member` / `membershipSyncContext` find it in the provider's listing of the node, the row whose left is that peer, and walk it at its address; this is how the account's fos entry above Home is reached). Lookups: `memberEdgesOf`, `membershipOf`, `membershipIdOf`, `membershipPath`/`membershipPathAt`, `memberPeerOf`, `mapMembership`; memberships are not bookkeeping (`isBookkeepingEdge`) and `rowTypeOf` is null for them.

Memberships are children of their node in node exchange and sync in their own rounds, under the grants and masks that already apply: the owner's devices receive and push all of them (market listings, published offers, invitations, switches), another peer receives only its own entry and the rows it may read (a masked projection: a different-looking node with a subset of children). In an entry, grants and offers are `NodeChild.pinned` (the cid of their immutable node, content with the shape). Nothing else changed on the wire. Consequences: relay queues are ordinary rows of the recipient's entry (no step-in path, no `relayQueueSync`); the server's verify key is a row on the fos member entry of the account root again (no Home key row), which an owner's device pulls above Home (`NodeSyncContext.above`). Members granted `local` stay on the machine. Design: docs/sync.md, "On-demand node providers" and "Node sync". Tests: `member-sync.test.ts`, `relay.test.ts`, `users.test.ts`; backend `provideNode.test.ts`, `verify.test.ts`, `crossAccount.test.ts`; web `tests/relay.cjs`, `tests/users.cjs`.

- `primitives.ts` / `native-refs.ts` - `primitiveRef` constructs execute-only native values; runtime JavaScript meaning lives on the local graph node and is not serialized. Scoped ref declarations and their accepted submissions are the sole registration mechanism. `nativeRefValues` and `primitiveExecutors` traverse those declarations, respect disabled providers, and match instruction types. Bootstrap definitions restore local meanings but do not authorize execution without a ref in scope. A peer is reached the same way: a connection is the native of the peer's `provideNode` offer (`NodeTransport`: its capabilities, `attachment(address)`, `available()`, `request`), offered on its row at the device root (`offerNodeTransport`, published once, rebound after), and what reaches a peer from a node is that offer found by scope search (`nodeTransportAt`); nothing chooses a transport from a peer id (`node-transports.test.ts`).

## Structural row patterns

A row is [left, right]. The left is its instruction/pattern (type, constructor,
capability, or function); the right is its argument, handler, or composed function.
A node has no independent type annotation. Ref construction adds an ALIAS row and
an optional TARGET; it never adds a type instruction pointer. IP/TARGET pairs used
to encode whole rows in choice options and root envelopes are row serialization.

Patterns are graph nodes, checked by matchesGraph in structural.ts. Required rows
are products; choices are sums. Both sides match recursively. Empty pattern values
are unconstrained. Alias identities, history, and presentation do not establish a
type. A namedRefPattern("complete") constructs a ref and its title as rows; a row
with that left and an empty right requires the complete property with any value.
Each actual alternative must satisfy a whole allowed pattern; alternatives cannot
supply separate parts of one product. Native scalar constructors inspect leaf values.

Declarations and advertisements retain [pattern, ref] rows. Discovery receives the
pattern from that row and recursively inspects accepted submissions for subrefs.
Node exchange carries the left definition with a declaration; right-side metadata
only describes name/bound state. Values and their descendants load under their own
permissions. Binding, submission validation, and execution use structural matching.
Partial assignments may retain UUID holes; that does not make an input executable.
Compilation preserves sums as choice rows and retains outstanding hole identities
alongside the residual CID. Run requires a closed left side; right-side outputs may
remain open. Legacy library names and editor placement policies are adapters, not
intrinsic node types or an alternative handler registration mechanism.
